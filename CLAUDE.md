# Lokin — context for Claude

Personal single-user app for Jeff: cut fat, keep muscle. Everything lives in `index.html` (markup + CSS + ~400 lines vanilla JS). No framework, no build step, no backend — this is deliberate; don't introduce tooling unless Jeff asks for a capability that needs it (device sync, API imports).

## Loss rate target band is now dynamic — %/wk of trend weight, not fixed kg/wk (2026-08-13)
Jeff, after confirming the "range" he remembered was just the Loss Rate guardrail's own sub-text ("Right inside the 0.5–0.7 kg/wk band"): "can we make this dynamic because it should change depending on how much fat you have left... or a percentage of your current bodyweight/bodyweight trend." Chose %-of-trend-weight over a fat-mass-derived approach — simpler, well-established (0.5–1%/wk is the standard evidence-based range for losing fat while preserving muscle; it's the same guideline used earlier in conversation to sanity-check "3.56kg in 35 days"), and it already does what he wants indirectly: the same percentage naturally yields a *smaller absolute kg/wk number* as trend weight drops, without needing to model fat mass specifically (which would also risk fighting the Muscle-risk guardrail's already-deliberately-loose fat-ceiling logic).

- `DEFAULTS.config.rateLoPct`/`rateHiPct` (0.5, 1.0) replace `rateLo`/`rateHi` (were fixed kg/wk, 0.5/0.7). Existing users' old `rateLo`/`rateHi` values just sit orphaned in their saved config (harmless — `Object.assign` merge means the new `*Pct` keys get their fresh defaults since old configs don't have them yet, same non-migration pattern used for every other config addition in this app).
- `evalGuards()`'s Loss Rate check now computes `lo`/`hi`/`crit` freshly from `m.trendWeight` on every render: `lo = rateLoPct/100 * trendWeight`, same for `hi`; **the crit threshold is now also %-based** (`rateHiPct + 0.5`, i.e. half a point above the upper band edge) rather than the old flat `> 1.0` — a fixed kg/wk crit ceiling would've gotten relatively *looser* (a shrinking percentage) as bodyweight drops, exactly backwards from the muscle-preservation reasoning driving the whole change. This wasn't explicitly requested but follows directly from the same logic Jeff gave, so it was made consistent rather than left half-dynamic.
- The guardrail's message now shows both forms for transparency — e.g. "Right inside your 0.39–0.78 kg/wk (0.5–1.0% of 77.9 kg) band" — so the numbers are self-explanatory rather than looking like they came from nowhere when they no longer match what he remembers as "the" band.
- Targets panel: "Rate min kg/wk"/"Rate max kg/wk" → **"Rate min %/wk"/"Rate max %/wk"**, step size tightened to `0.05` (percentages are naturally smaller numbers than the old kg values).
- `buildAnalysisPrompt()`'s payload field renamed `rate_band_kg_wk` → `rate_band_pct_bodyweight_per_wk` — the AI already receives `trend_kg` separately, so it can derive the current kg/wk equivalent itself rather than being sent a stale fixed number.
- New smoke test (14 days of weight loss at a fixed 0.6 kg/wk pace, but starting from a *low* 40kg trend weight instead of Jeff's real ~76-79kg) confirms the same absolute rate that reads "On track" for Jeff's actual bodyweight (test 2, unchanged, still passes) reads "too fast" at a much lower trend weight — proving the band actually recomputes rather than just having its config keys renamed. Verified live in-browser too (both the guardrail text and the renamed Targets fields).

## Overview page draggable sideways — CSS overflow-x gotcha (2026-08-13)
Jeff: "why is the overview page not locked in place, it's like able to be moved left and right on the same page." Root cause: `.page { overflow-y: auto; }` with no `overflow-x` set. Per the CSS Overflow spec, if one axis is explicitly non-`visible` and the other is left unspecified, the browser computes the *unspecified* one as `auto` too rather than leaving it `visible` — so `.page` was silently `overflow-x: auto` this whole time, meaning ANY horizontal overflow (even sub-pixel) makes the page itself draggable/scrollable sideways, on top of (and confusable with) the pager's own intentional horizontal swipe between tabs. Fixed with an explicit `overflow-x: hidden` on `.page`. **Could not reproduce an actual overflowing element** to name the root trigger — tried realistic seeded data (21 days of entries, strength sets) at 390px and 375px widths, `page.scrollWidth` matched `clientWidth` exactly both times, no element found overflowing the page's right edge. The fix is applied regardless since it's the standard, correct default for a single-purpose scroll container like this regardless of what was overflowing — but if this recurs, the next debugging step is checking on Jeff's actual device/viewport width rather than trying to reproduce here, since it may be state- or width-specific to his real usage (a particular guardrail combination, a longer verdict message, or an iOS-Safari/WKWebView subpixel-rounding difference from Chrome).

## Progress photo "doesn't seem to be working" (2026-08-13) — diagnostics added, not yet confirmed fixed
Expected, given the 2026-08-12 CLAUDE.md note already flagged this exact feature as **unverified on real hardware** (only the web fallback path — a different code branch — had been tested). Root problem found on inspection, not by reproducing the failure: every native-only failure point in the photo flow was silently swallowing its error —
- `progressCamera.getPhoto()`'s `.catch(() => {})` treated a genuine plugin/permission failure identically to a user backing out of the picker — both produced total silence.
- `nativeFS.getUri()` (used to resolve a saved photo back to a displayable `capacitor://` URL) failing just fell back to `cb(null)`, which `renderPhotoBox()` renders as "+ Add progress photo" — **identical to no photo ever having been attached**, even if `writeFile` had already succeeded and `state.entries[].photo` genuinely has the path. This is the prime suspect: the write likely works (it's a simple, well-trodden Filesystem call), the *read-back* (`getUri` + `Capacitor.convertFileSrc`) is the newer, less-proven half of the round trip, and its failure is the one that would make the UI look exactly like "nothing happened."
- `nativeFS.writeFile()`'s catch already alerted, but with a generic "Couldn't save the photo." — no actual error text.

Fixed all three to surface the real error text (in the button's own label, or via `alert()` for the write failure) instead of failing silently — same pattern that actually resolved the 2026-07-19/20 HealthKit debugging saga ("surface the real error/state... before proposing another fix"), applied proactively here since a blind second fix attempt without knowing which of the three points is actually failing would just be another guess. **Still needs Jeff to try again on a rebuild and report back what the button now says** — that will pin down which of the three failure points it actually is, rather than guessing further. ## iOS app (Capacitor)
`ios/` is a Capacitor 7 wrapper around the same `index.html`, **bundled mode** (not hybrid/remote — a `server.url` experiment on 2026-07-19 broke the native plugin bridge in ways described below and was reverted same day). `npm run build:www` copies web files + `capacitor.js` into `www/`; `npm run ios` = build + sync + patch + open Xcode; `npm run ios:sync` does the same without opening Xcode (use this to verify a build compiles). Requires Xcode 16+ (13.x fails compiling Capacitor 7 — Jeff updated 2026-07-20).

**Consequence of bundled mode**: the native app needs an Xcode rebuild+reinstall to pick up any `index.html`/plugin change — not just the weekly re-sign. Since re-signing already requires cable+Xcode+▶ weekly regardless (free Apple ID, 7-day cert expiry — the $99/yr program removes this), that's the natural moment to also grab pending changes; rebuild sooner only if something's urgent. ## What the app does
- Weight displays at 2 decimal places everywhere it's *measured/tracked* data (log table, chart tooltip, Trend weight stat, Lost so far, "kg to go") — bumped from 1 decimal 2026-07-25. Goal targets (74.0/72.2 kg) and chart axis tick labels stay at 1 decimal on purpose: they're round targets / synthetic scale marks, not logged measurements, so extra precision there would be noise. `f-weight` input already accepted `step="0.01"`; this was purely a display-formatting gap (`fmt(x, 1)` → `fmt(x, 2)` at the relevant call sites).
- Daily log (date / weight kg / kcal / protein g) → localStorage under key `cutTracker.v1`. Partial entries fine; fields merge per date. Entries also carry `carbs`/`fat` (added 2026-07-26, populated via Chat estimates or Health sync only — no manual input field yet) and an optional `photo` (added 2026-08-12 — see the Progress photos note above for the native-file-vs-web-data-URL storage split).
- Trend chart: raw weigh-ins as faint dots, 7-day trailing average as the line, dashed goal lines at 12% (74 kg) and 10% (72.2 kg). Mark legend below; 1w/1m/All range chips (`config.chartRange`) window the chart *display only* — regression and averages always use full data. **"Lost so far" stat now tracks the same range chip** (2026-07-25): All uses the true `c.startWeight` anchor (unchanged); 1w/1m compare current trend weight against the earliest trend point actually shown in that window (`m.trend.find(p => p.x > m.latest - span)`), so the number always matches what the chart is currently displaying. Caption shows the *actual* day count found, not a hardcoded 7/30 — honest when there is less history than the window requests. Fixed an off-by-one the same day: the window filter uses strict `>` (matching the chart's own filter), so the earliest included point for "1w" is `latest-6`, not `latest-7` — the window itself already correctly spans 7 days, but the label needs `m.latest - ref.x + 1` (inclusive count), not the raw gap, or it undercounts by one ("in past 6 days" instead of 7). "1m" is a deliberate 30-day rolling window, not a literal calendar month — same convention as Apple Health/stock charts' "1M".

  6. **Strength** — recent-21-day best e1RM (Epley) per benchmark lift vs cut-best, worst lift judged: ≥97% good, 92–97% warn, <92% crit. Needs ≥2 sets per lift. ## Non-obvious design decisions (don't silently reverse)
- **Loss rate = linear regression** over the last 21 days of weigh-ins, widening to all data when the window has <2 points or <7 days span. Never day-to-day deltas — daily swings are glycogen/water.
- **Muscle risk uses the intake deficit, not the scale-derived one.** Early-cut water/glycogen losses make kg-on-the-scale × 7,700 kcal wildly overstate the true deficit and would contradict the other cards.
- **Muscle-risk bands are deliberately loose** (good ≤ ceiling+200, warn to +450, crit beyond): Jeff's *planned* 500 kcal deficit slightly exceeds the ~381 fat ceiling. If on-plan reads yellow forever, the signal dies. Keep "on-plan = green".
- Verdict priority is crit > warn > good, first match in guardrail order — deliberate, so under-eating outranks everything else at equal severity.
- Weekly averages over daily numbers, everywhere, in every message shown to Jeff.
- **Visual identity** (2026-07 pass): "clinical instrument" — cool grey-blue neutrals, tabular mono numerals, severity colors. Wordmark + day counter use Avenir Next Condensed via `--display` (ships on Apple platforms; no font files — CSP). The signature element is the segment strip in the verdict hero (RATE·KCAL·FLOOR·MUSCLE·PROTEIN·LIFTS·STEPS — plain words; Jeff couldn't parse cuter abbreviations), one tick per guardrail in card order, tap scrolls to the card — it exists to make the "verdict = worst of X" logic visible; don't decorate it or reorder it away from the guardrail order. **Update (2026-08-13): no longer always seven.** A disabled guardrail's segment is dropped from the strip too, matching its guardrails-list card — see the note below. The strip still preserves relative order among whatever segments remain, and still means "verdict = worst of what's currently on."

- The page is published as an artifact: strict CSP, no external requests, so it must stay fully self-contained (it already is — keep it that way).
