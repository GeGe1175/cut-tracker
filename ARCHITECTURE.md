# Lokin — how the codebase works

A walkthrough of every file in this repo and how the app fits together. If you just want to make a specific kind of change, skip to **"If you want to change X"** at the bottom.

## The big idea

Lokin is one HTML file. `index.html` contains the entire app — markup, CSS, and JavaScript — with no framework, no build step, and no backend. Every screen you see, every calculation, every button, lives in that one file.

That same file gets wrapped into a **native iOS app** using a tool called Capacitor, which is basically "put a website inside a native app shell, and give it a bridge to talk to real device features" (camera, HealthKit, the filesystem). The native wrapper is the `ios/` folder. It doesn't contain any of the app's actual logic — it just loads `index.html` inside a native window (a WKWebView) and provides plugins that JavaScript can call into for things a website normally can't do (read your camera roll, write files, read Apple Health).

There's no server anywhere. Everything you log stays on your device, in `localStorage` — the browser's/WebView's built-in key-value storage. Nothing gets uploaded unless you explicitly export a backup or use Coach's report (which copies data to your clipboard, or in the past sent it directly to Anthropic's API).

## File-by-file map

### Root files (the actual source you edit)

| File | What it is |
|---|---|
| **`index.html`** | The entire app. ~2000 lines: a `<style>` block (all CSS), then a `<script>` block (all JS). This is the only file that matters for "how does the app behave." |
| **`capacitor.config.json`** | Capacitor's settings — app ID, app name, which folder holds the web files (`www`), an iOS-specific setting (`contentInset`), and `packageClassList` (which custom native plugins to register — see the HealthSyncPlugin section below). This is the *source*; a copy gets generated inside `ios/` on every sync. |
| **`package.json`** | npm scripts — how you run/test/build the project. See "Dev workflow" below. |
| **`manifest.webmanifest`, `sw.js`, `apple-touch-icon.png`, `icon-192.png`, `icon-512.png`** | PWA (installable-website) bits, used only by the legacy GitHub Pages version. Not relevant to the native app. |
| **`smoke.js`** | The test suite. Run with `npm test`. Loads `index.html`'s `<script>` into a fake, minimal browser (no real DOM, no real windows) and asserts that things like guardrail verdicts, imports, and the Coach's-report payload come out correct. |
| **`scripts/patch-ios-config.js`** | A small fixup script that runs after every native sync — explained in detail below, it's working around a real Capacitor limitation. |
| **`README.md`** | Quick human-facing "how do I run this" reference. |
| **`CLAUDE.md`** | Not app documentation — this is *my* (Claude's) persistent memory about this project: decisions made, bugs found and fixed, why things are built the way they are, dated notes from past sessions. Worth skimming if you're curious about the history/reasoning behind something, but it's written for an AI picking the project back up, not as a clean reference. |

### `ios/` — the native wrapper

| File/folder | What it is |
|---|---|
| **`ios/App/App.xcworkspace`, `App.xcodeproj`** | The Xcode project. This is what you open (or `npm run ios` opens for you) to build and run on your phone/simulator. |
| **`ios/App/App/AppDelegate.swift`** | Standard Capacitor boilerplate, untouched. Handles app lifecycle events (launch, background, foreground) — Capacitor's own plugin system hooks into this automatically. |
| **`ios/App/App/HealthSyncPlugin.swift`** | The one custom native plugin in this project — reads and writes Apple Health data. Full section below. |
| **`ios/App/App/Info.plist`** | iOS app metadata: display name, permission strings (why the app wants camera/photo/Health access — these are the exact sentences iOS shows you in the permission popup), supported orientations. |
| **`ios/App/App/Assets.xcassets/`** | The app icon (`AppIcon.appiconset`) and launch-screen image (`Splash.imageset`). |
| **`ios/App/App/capacitor.config.json`** | *Generated* — a copy of the root `capacitor.config.json`, regenerated by `cap sync` and then patched. Don't hand-edit this; edit the root one. |
| **`ios/App/App/public/`** | *Generated* — the actual web files the native app loads (a copy of `www/`, which is itself a copy of `index.html` + friends). Don't hand-edit this either. |
| **`ios/App/Podfile`, `Podfile.lock`** | CocoaPods dependency list — the native iOS libraries Capacitor and its plugins need (Camera, Filesystem, Share). Managed automatically by `cap sync` / `pod install`. |
| **`www/`** | *Generated*, gitignored — the staging copy `npm run build:www` creates from `index.html` before it gets synced into `ios/App/App/public/`. |

The three generated things (`www/`, `ios/App/App/public/`, `ios/App/App/capacitor.config.json`) are all gitignored — they're rebuilt from source every time, never hand-edited, never committed.

## How `index.html` is organized

Open it and you'll find, top to bottom:

1. **`<meta>` tags and `<title>`** — standard page setup, plus the PWA/app-icon hookup.
2. **One big `<style>` block** — every CSS rule in the app. Uses CSS custom properties (`--bg`, `--accent`, `--ink`, etc.) defined once at the top and reused everywhere, with a `@media (prefers-color-scheme: dark)` block that overrides them for dark mode. That's the whole theming system — swap the variables, everything using them updates.
3. **The HTML body** — four `<section class="page">` blocks (Strength, Log, Overview, Coach) sitting inside a horizontally-scrollable `.pager`, plus a `.tabbar` with the four tab buttons. A fifth page (`page-chat`) exists but is commented out — see "Chat" below.
4. **One big `<script>` block** — every line of JavaScript, wrapped in a single `(function () { ... })()`. That wrapping is deliberate: it means nothing inside leaks into the global scope, so this file can't accidentally clash with anything else on a page (matters for the legacy web/artifact hosting).

Inside that script, roughly in file order:

- **State model** (`DEFAULTS`, `load()`, `save()`) — what gets stored and how.
- **Helpers** — date math, number formatting, sorting.
- **Guardrail evaluation** (`evalGuards`, `metrics`, `verdict`) — the core "is Jeff on track" logic.
- **Chart drawing** (`drawChart`) — hand-rolled SVG, no charting library.
- **`render()`** — the one function that repaints the whole UI from current state.
- **Per-feature render/wire functions** — `renderLog`, `renderStrengthDetail`, `renderSettings`, `renderGuardToggles`, `renderPhotoBox`, etc. Each owns one piece of the screen.
- **Native bridge detection** (`nativeFS`, `nativeShare`, `progressCamera`, `nativeHealth`) — explained below.
- **Apple Health import/sync**.
- **Coach's report** — builds a JSON summary and copies it (with a prompt) to your clipboard.
- **Chat** — the disabled photo-logging-via-Claude feature, kept but inert.
- **The pager** — swipe/tap navigation between the four tabs, at the very bottom.

## The data model

Everything lives in one JavaScript object called `state`, saved to `localStorage` as a single JSON blob under the key `cutTracker.v1`:

```
state = {
  config: { ...all your targets and settings... },
  entries: [ {date, weight, kcal, protein, carbs, fat, steps, photo}, ... ],  // one per logged day
  strength: [ {date, lift, w, reps}, ... ],                                   // one per logged set
  chat: [ ... ]                                                               // dormant, Chat feature only
}
```

- **`entries`** is your daily log — one row per date, fields filled in as you log them (a day can have just a weight, or just kcal, etc. — nothing's required together).
- **`strength`** is every individual set you've logged on a benchmark lift.
- **`config`** holds every number you can edit in Targets (RMR, calorie target, protein target, rate band, goal weights, fat mass, step baseline, benchmark lift names) plus `guardrailsOn` (which of the seven guardrails are currently enabled).

Two things live *outside* `state`, in their own separate `localStorage` keys, on purpose: your Anthropic API key (`cutTracker.apiKey` — dormant now that Coach's report no longer uses it) and your last-backup timestamp (`cutTracker.lastBackupAt`). Both are deliberately excluded from `state` so that exporting/importing a backup never carries a secret key along with it, and so restoring an old backup doesn't reset your "haven't backed up in a while" reminder.

`load()` merges saved config with `DEFAULTS.config` (so a new setting added in an app update gets its default value instead of `undefined` for existing users) and falls back to a totally empty state if nothing's saved yet.

## The render loop

There's no framework managing updates — it's all manual. The pattern is: **change `state`, call `save()`, call `render()`**. `render()` recomputes everything from scratch and overwrites the relevant chunks of the page with fresh HTML (`element.innerHTML = "..."`). It's simple and a little wasteful (it rebuilds things that didn't change), but at this scale that's not a real cost, and it means there's never a "did I remember to update the UI" bug — `render()` always reflects current `state`, full stop.

The pipeline inside `render()`:

1. **`metrics()`** crunches the raw log into derived numbers — 7-day averages, the regression-based loss rate, trend-line points for the chart, days of data available, etc.
2. **`evalGuards(metrics)`** turns those numbers into a verdict for each of the seven guardrails (good/warn/crit/no-data/off).
3. **`verdict(metrics, guards)`** picks the single worst active guardrail and turns it into the headline message you see at the top of Overview.
4. Everything else — the verdict hero, the segment strip, the readouts, the chart, the guardrail cards, the log history, the strength summary — gets painted from those three results.

## The guardrails system

This is the heart of the app. Seven fixed checks, always evaluated in the same order:

```
GUARDRAIL_IDS    = ["rate",      "kcal",              "floor",       "muscle",      "protein", "strength", "steps"]
GUARDRAIL_LABELS = ["Loss rate", "Eating your target", "Energy floor","Muscle risk", "Protein", "Strength", "Activity"]
```

Those two arrays are the single source of truth for guardrail order — `evalGuards()` pushes results in this order, the segment strip renders labels in this order, and the Targets toggles list them in this order. Add an eighth guardrail and these two arrays are the first thing to update.

Each guardrail is individually switchable via `state.config.guardrailsOn`. Turning one off doesn't just grey it out — it removes that guardrail from *everywhere*:
- Excluded from the verdict (can never drive the headline message, even if it would otherwise be a crit).
- Its card disappears from the Guardrails list on Overview.
- Its tick disappears from the segment strip (the rest reflow to fill the space).
- Its column disappears from the Log page's history table and its field disappears from the Log form (rather than showing a confusing "—", which used to look identical to "nothing logged").
- Its data is stripped from the Coach's-report payload, so the AI never sees or comments on it.

The one function that decides "is this field's data safe to show right now" is `guardrailDataVisible()` — everything above (the Log page, Coach's report) calls it rather than each re-implementing the same logic. One exception: `kcal`/`floor`/`muscle` all read from the *same* underlying kcal number, so that figure is only hidden once all three of those guardrails are off, not just one — otherwise a still-enabled guardrail would lose the data it needs to be judged. Weight always stays visible regardless of the "rate" toggle — it's the app's core measurement, not itself "unreliable" the way a Health-sync gap makes kcal/protein/steps unreliable.

## The native bridge pattern

Every native capability in this app follows the same shape:

```js
const someNativeThing = (function () {
  try {
    if (window.Capacitor && window.Capacitor.isNativePlatform && window.Capacitor.isNativePlatform() &&
        window.Capacitor.registerPlugin) {
      return window.Capacitor.registerPlugin("PluginName");
    }
  } catch (e) {}
  return null;
})();
```

On the native app, this resolves to a working plugin object. On the web (GitHub Pages, or `npm run dev` on localhost), `window.Capacitor` either doesn't exist or reports it's not native, so this resolves to `null` — and every call site checks for that and falls back to a web-appropriate alternative (or just does nothing). This is why the same `index.html` works in both places: native features degrade gracefully rather than crashing.

The four bridges currently in use:

- **`nativeFS`** (`Filesystem`) — writes the Export backup file, and writes/reads progress photos.
- **`nativeShare`** (`Share`) — hands the exported backup to iOS's native Share sheet.
- **`progressCamera`** (`Camera`) — opens the photo/camera picker for progress photos.
- **`nativeHealth`** (`HealthSync` — our own plugin, see next section) — reads Apple Health data.

A fifth, **`nativeCamera`**, exists but is dormant — it's Chat's own camera reference, defined inside Chat's disabled code block, unreachable while Chat is off.

## `HealthSyncPlugin.swift` — the one custom native plugin

Every other plugin this app uses (Camera, Filesystem, Share) is an official Capacitor plugin, installed via npm. HealthKit access isn't something Capacitor ships out of the box, so this project has one hand-written Swift plugin for it, with two methods:

- **`readDaily(days)`** — pulls weight, calories, protein, carbs, fat, and step count from HealthKit for the last N days, and hands back rows shaped exactly like the app's own daily-entry format, so the JS side can reuse its normal import/merge logic unchanged.
- **`writeFood(date, kcal, protein, carbs, fat)`** — writes nutrition data *into* HealthKit. This exists for Chat's "add to today" flow, so a Chat-logged meal would also show up in Health (and reconcile with anything MyFitnessPal writes there). Currently dormant, since it's only called from Chat's disabled code.

**A real Capacitor quirk worth knowing**: unlike official npm plugins, a hand-written local plugin like this one is *not* auto-discovered. Capacitor's native bridge only knows to register it because its class name is listed in `packageClassList` inside `capacitor.config.json`. The catch: running `npx cap sync` recomputes that list from your installed npm plugins and would silently *wipe* the hand-added `HealthSyncPlugin` entry every time — which is exactly what `scripts/patch-ios-config.js` exists to prevent. It runs right after every sync and re-adds `HealthSyncPlugin` back into the generated config, without disturbing the official plugins that `cap sync` already added correctly on its own.

## The pager (swipe navigation)

`.pager` is a horizontally-scrolling flex container with CSS scroll-snap; each `.page` is one full-width slide. The four tab buttons in `.tabbar` and the four `.page` sections have to stay in the *same order* in the DOM — the pager script reads tab order once at startup (`Array.from(document.querySelectorAll(".tab"))`) and uses each tab's position as an index into scroll position (`index * pager.clientWidth`), so a tab and its matching page need to occupy the same position in both lists. Move a tab, move its page section to match.

Tapping a tab or scrolling calls `goTo(pageId)`, which scrolls to `index * pager.clientWidth` and marks that tab active. On page load, `goTo("page-home", false)` lands you on Overview immediately, no animation.

## What's live right now vs. dormant

**Active:** Strength, Log, Overview, Coach tabs; all seven guardrails (individually toggleable); strength personal records with per-weight trend charts; progress photos; automatic Health read-sync on launch/foreground; Export/Import backup; Coach's report (clipboard-to-Claude-app only, no direct API calls).

**Disabled but intact:** the Chat feature (food-photo logging via a direct Claude API call) — its HTML is commented out and its JavaScript is wrapped in a guard that never runs, but nothing was deleted. It needs a paid Anthropic API key that isn't covered by a Claude Code subscription, which is why it's off. Re-enabling it means uncommenting the markup and removing the JS guard — see `CLAUDE.md` for exactly where.

**Legacy:** the web/PWA surface (GitHub Pages hosting, the service worker, the manifest) still technically works but isn't part of daily use anymore — the native iOS app is. `npm run dev` (localhost) is still useful as a quick visual sanity-check since it's the same HTML/CSS the native WKWebView renders, but it can't exercise anything that needs a real native plugin (camera, filesystem, Health).

## Dev workflow

- **`npm run dev`** — serves the folder at `localhost:8000`. Fast way to eyeball a change, but no native capabilities.
- **`npm test`** — runs `smoke.js`, a headless test suite that boots the app's own script under a minimal fake DOM and checks that guardrail verdicts, imports, and generated payloads come out right. No browser needed.
- **`npm run ios:sync`** — copies `index.html` + friends into `www/`, runs `npx cap sync ios` (updates the native project, installs CocoaPods dependencies), then re-patches `packageClassList`. This is the way to verify a change actually compiles into the native app without opening Xcode.
- **`npm run ios`** — the same, plus opens the Xcode project.
- Actually *running* the app on a phone or simulator still requires Xcode itself (hit ▶) — there's no way to fully verify a native feature (camera, Health, filesystem) without that.

## If you want to change X, look at Y

| You want to... | Look at |
|---|---|
| Change a guardrail's thresholds or logic | `evalGuards()` |
| Add a new guardrail | `evalGuards()`, plus add its id/label to `GUARDRAIL_IDS`/`GUARDRAIL_LABELS` and a default in `DEFAULTS.config.guardrailsOn` |
| Change what a disabled guardrail hides | `guardrailDataVisible()` |
| Change the weight trend chart | `drawChart()` |
| Change the per-weight strength chart | `weightChartSVG()` |
| Add a new tab/page | Add a `.tab` button *and* a matching `.page` section in the same relative DOM position |
| Change default targets (RMR, calorie target, etc.) | `DEFAULTS.config` |
| Change a native permission's description text | `ios/App/App/Info.plist` |
| Add a new native plugin | npm-install it, it'll auto-register via `cap sync`; only *hand-written* local plugins need adding to `OUR_LOCAL_PLUGINS` in `scripts/patch-ios-config.js` |
| Change the color theme | The CSS custom properties at the top of the `<style>` block (`--bg`, `--accent`, etc. — light and dark variants) |
| See why something is built a certain way | `CLAUDE.md` — searchable, dated history of past decisions and bugs |
